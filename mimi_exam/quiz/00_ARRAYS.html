01-B. Arrays

Q1
In C++, if an array is declared as int a[5];, what is the valid index range for accessing its elements?
C++ arrays are 0-indexed. An array of 5 elements has valid indices 0, 1, 2, 3, and 4.
Q2
In an array, what is the difference between capacity and size?
Capacity is the total space allocated for the array, fixed at allocation time. Size is the number of elements actually in use right now, which can be less than or equal to the capacity.
Q3
What does it mean for an array to be stored in 'contiguous memory'?
Contiguous means the elements are laid out back-to-back in memory. This is what allows an array to compute any element's address directly from its index, giving O(1) access.
Q4
What happens in C++ if you access a[10] on an array declared as int a[10]; (which only has valid indices 0 to 9)?
Unlike some higher-level languages, C-style arrays in C++ do not perform automatic bounds checking. Accessing an out-of-range index is undefined behavior — it might read garbage memory, crash, or appear to work by accident.
Q5
Given int a[8]; on a machine where sizeof(int) == 4 and a begins at address 0x1000, what is the address of a[5]?
Each int takes 4 bytes, so a[5] is 5 * 4 = 20 bytes after the start. 0x1000 + 20 (0x14) = 0x1014.
Q6
For int a[10];, which expression is equivalent to &a[2] (the address of the third element)?
The array name a decays to a pointer to its first element. Adding 2 to that pointer moves it forward by 2 elements (pointer arithmetic accounts for the element type, not raw bytes), which is exactly &a[2].
Q7
A function is declared as void show(int arr[]). Inside show, what does sizeof(arr) actually return?
When an array is passed as a function parameter, it decays into a pointer to its first element. Inside the function, arr is really an int*, so sizeof(arr) returns the size of a pointer (commonly 8 bytes on a 64-bit system), not the size of the original array.
Q8
For int a[10]; declared inside main() (with sizeof(int) == 4), what does sizeof(a) evaluate to inside main()?
Inside the function where the array is declared, the compiler still knows its full type, int[10], so sizeof(a) correctly returns 10 * sizeof(int) = 40 bytes.
Q9
What does this program print? (Assume sizeof(int) == 4 and sizeof(int*) == 8.)
void show(int arr[]) {
    std::cout << sizeof(arr) << "\n";
}
int main() {
    int data[6] = {1,2,3,4,5,6};
    std::cout << sizeof(data) << "\n";
    show(data);
}
In main(), data is a real array of 6 ints, so sizeof(data) = 6 * 4 = 24. When data is passed into show(), it decays to a pointer, so sizeof(arr) inside show() is the size of a pointer, 8. Output: 24 then 8.
Q10
When an array is passed to a function as int arr[], what information about the original array is lost inside the function?
Because the array decays to a plain pointer, the function only receives the address of the first element. The original size is not carried along automatically — it must be passed separately, for example void f(int arr[], int n).
Q11
What is the worst-case time complexity of accessing an element at index i in an array?
Arrays store elements in contiguous memory, so the address of index i can be computed directly (base + i * element size) without searching. This makes access O(1).
Q12
What is the worst-case time complexity of searching for a value in an unsorted array of size n?
Without any ordering to exploit, we may need to check every element before finding the value or confirming it is absent, giving O(n) in the worst case.
Q13
What is the worst-case time complexity of inserting a new element at the front of an array of size n, assuming there is spare capacity?
Inserting at the front requires shifting every existing element one position to the right to make room, which takes O(n) time.
Q14
Assuming there is spare capacity, what is the time complexity of inserting a new element at the end of an array?
If there is already room, inserting at the end just writes to the next free slot and updates the size, with no shifting needed, so it is O(1).
Q15
What is the time complexity of deleting an element from the middle of an array of size n?
After removing an element from the middle, every element after it must shift one position to the left to close the gap, which takes O(n) time.
Q16
In an array, which operation is generally more expensive: inserting at the front, or inserting at the end, assuming there is spare capacity?
Inserting at the end, with spare capacity, just writes to the next free slot: O(1). Inserting at the front requires shifting every existing element one position to the right first, which takes O(n).
Q17
Trace this code. What is the final content of v?
std::vector<int> v;
for (int i = 0; i < 5; ++i) v.push_back(i * i);
v.erase(v.begin() + 1);
v.insert(v.begin() + 2, 99);
push_back fills v with 0, 1, 4, 9, 16 (i*i for i=0..4). erase(begin()+1) removes the value at index 1, which is 1, giving [0,4,9,16]. insert(begin()+2, 99) inserts 99 at index 2, giving [0,4,99,9,16].
Q18
A std::vector doubles its capacity whenever it becomes full. Why does a sequence of n push_back calls cost O(n) in total, instead of O(n^2)?
Most push_back calls are O(1) because there is room. When the vector is full, resizing costs O(n) to copy everything into a new, larger buffer, but this only happens O(log n) times. Spreading that copying cost over all n push_back calls gives O(1) amortized time per call, so the whole sequence is O(n), not O(n^2).
Q19
A vector starts with capacity 1 and doubles every time it fills up (1 -> 2 -> 4 -> 8 -> ...). About how many reallocations happen while pushing 1000 elements?
Capacity doubles: 1, 2, 4, 8, 16, 32, 64, 128, 256, 512, 1024. It takes about 10 doublings to pass 1000, so around 10 reallocations occur, far fewer than one per push_back.
Q20
After calling v.erase(v.begin()) on a std::vector, what typically happens to its capacity()?
erase() removes an element and shifts the rest, reducing size(). It does not automatically shrink the underlying buffer, so capacity() usually stays unchanged unless you explicitly call something like shrink_to_fit().
Q21
When should you generally prefer std::vector over a raw C-style array in C++?
std::vector manages its own memory and can grow or shrink at runtime, which is exactly what you want when the size isn't fixed at compile time. A raw C-style array has a fixed size decided when it is declared.
Q22
Once a C-style array like int a[10]; is declared, can its capacity be changed later in the program?
A C-style array's size is fixed at the point of declaration and cannot grow or shrink afterward. To get a resizable array, you would need std::vector, or manually allocate a new, larger array and copy the data over.
Q23
This function has a bug.
int* buildRow(int n) {
    int row[100];
    for (int i = 0; i < n; ++i) row[i] = i;
    return row;
}
What is wrong with it?
row is a local array stored on the stack. Once buildRow() returns, that stack memory is no longer valid, so the returned pointer is dangling. Using it afterward is undefined behavior — this is different from a memory leak, where the memory is valid but never freed.
Q24
What is the correct way to fix the buildRow() bug above?
The safest fix is to allocate the array on the heap (remembering to delete[] it later) or, in modern C++, simply return a std::vector by value — it manages its own memory safely and correctly outlives the function call.
Q25
You are implementing void rotateLeft(int a[], int n, int k); to rotate an array left by k positions. If k could be larger than n (for example, n=5 and k=12), what should you do first?
Rotating an array of size n by exactly n positions returns it to its original order, so any rotation amount repeats every n steps. Taking k % n first reduces k to a safe range (0 to n-1) before the actual rotation.
Q26
Rotating the array [1, 2, 3, 4, 5] left by 2 positions gives which result?
Rotating left by 2 moves the first 2 elements (1 and 2) to the end: [3, 4, 5, 1, 2].
Q27
You need to rotate an array in place using only O(1) extra space, with no second array. Which general technique achieves this?
A classic trick: reverse the entire array, then reverse the first n-k elements, then reverse the last k elements. This produces the rotated array using only a constant amount of extra space.
Q28
You need to store scores for an unknown number of students. Students are frequently appended, but rarely removed from the middle. Which structure is usually the better choice, and why?
Since appends are frequent and middle-removals are rare, a dynamic array's strengths (contiguous memory, cache-friendly access, O(1) amortized push_back) outweigh its one weakness here (O(n) removal from the middle, which barely comes up). A linked list avoids that weakness but pays for it with pointer overhead per node and worse cache performance.
Q29
Why do arrays generally have better cache performance than linked lists when accessing elements sequentially?
Because array elements sit next to each other in memory, accessing one element often pulls nearby elements into the CPU cache too, making the next accesses faster. Linked list nodes can be scattered anywhere in memory, so each node access can cause a separate, slower cache miss.
Q30
Compared to a plain array, what extra memory overhead does a singly linked list have per element?
Besides the actual data, each linked-list node also stores a pointer to the next node. An array has no such per-element overhead — elements are packed back-to-back in memory.
